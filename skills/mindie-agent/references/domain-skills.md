# Domain tooling

Remote-dev is a general tool. Serving or calling it never activates MindIE,
touches a knowledge lease, or creates capture state.

Jobs and artifacts are owned by the native Kimi session that bound the
`request_nonce`. Do not operate on another task's `job_id`. After a plugin
update, poll or stop an existing job with the same id; do not mix an old
script with a new interpreter on one call.

If a remote mutation's result is uncertain, inspect its existing receipt or
job before deciding what to do. Explicit recovery of a paused remote failure
circuit is `/mindie-agent:recover` in this native task — still without a
model-selected session id.

## Graded Knowledge Protocol, Progressive Loading, Reference Identity & `knowledge_distill`

- **Graded `knowledge_query` Parameters, Multi-Domain Routing & Response Shape (`graded-bm25`)**:
  - `knowledge_query` accepts `query`, optional `domain` (explicitly selecting the default domain or a registered `domain_configs` Engine/Feed such as `"vllm-ascend"` or `"operators"`; cross-domain references use existing `source_locator` / `evidence_refs` links rather than automatic federated retrieval), `limit` (`1..20`), `conditions`, `continuation`, `domain_path`, `token_budget` (`1..16000`, default `800`), `include_unknown` (default `false`), `include_archived` (default `false`; archived/superseded units stay hidden unless true or fetched by exact ref), and `request_nonce`.
  - **Step 1 — bounded navigation**: the response returns `cards[]` plus deduplicated `foundation_cards[]` (and the compatible `results[]` view); serialized usage is reported in `usage`. Discover candidate units from these cards first; do not treat a card summary as an executable contract or load every candidate body.
  - When a graded corpus is installed (`retrieval: "graded-bm25"`, `page: "graded_units"`), `cards[]` / `results[]` items return:
    - `id` (stable path-independent `unit-...` ID),
    - `ref = "mindie://<domain>/units/<id>@<revision>"` — the single-line `id@revision` identity, where `<revision>` is a positive integer; the reference is complete as returned and needs no derived fingerprint,
    - `unit_ref = "mindie://<domain>/units/<id>"` (stable unit URI without revision),
    - `feedback_ref = ref` (the same revision URI for graded units),
    - `revision`, `match_status` (`matched` | `mismatched` | `condition_unknown`), `missing_conditions`, `tier`, `category`, `evidence_strength`, `domain_path`, `conditions`, `provenance`, `excerpt`, `inherited_rules` (each with its own `ref`), and `inheritance_excluded`.
- **Step 2 — `knowledge_explain` Progressive Loading & `knowledge_feedback` Usage Events**:
  - Load only the selected references: `knowledge_explain(ref=..., request_nonce=...)` reads one exact current reference, while `knowledge_explain(refs=[...], conditions=<observed facts>, known_refs=[<already fully visible id@revision>], token_budget=<1..16000>, request_nonce=...)` assembles a batch closure. The batch computes `needed = closure(S) - visible_complete_refs`, expands shared prerequisites once in `requires`, and returns primary units in `units` without truncating their steps. `known_refs` means exact revisions already complete in the current context, not every unit opened earlier in the session. `ref` or `refs` may be used; when both are present, `ref` selects the routing engine, and all `mindie://` authorities in the request must agree or the call is rejected.
  - Pass the actual returned `ref` (`mindie://<domain>/units/<id>@<revision>`, a positive integer revision) or `unit_ref` to `knowledge_explain`, and copy the actual returned `feedback_ref` to `knowledge_feedback(ref, request_nonce, ...)` (**never pass a bare `id` or synthesize a ref**; for graded units `ref` and `feedback_ref` share the same revision URI value, whereas legacy material keeps task/block `ref` and `feedback_ref` distinct without mixing their roles). Both tools route by the URI authority domain (`mindie://<domain>/...`) while preserving `request_nonce` on every call, and feedback requires the returned revision URI (`feedback_ref` / `/units/<id>@<revision>` for graded units, or legacy `feedback_ref` for legacy material).
  - **Four-stage usage feedback** uses optional `event_type` on the same exact `feedback_ref`: `discovered` (query delivery; the server records it as `delivered`), `loaded` (complete explain read), `applied` (the unit changed an actual decision or action), and `evaluated` (requires `run_id` and `outcome="supported" | "refuted" | "inconclusive"`; `step_id` identifies the step). `run_id` binds the usage to a managed run and deduplication is per `(root_opaque, unit_id, revision, event_type, run_id)`. Legacy `rating="up" | "down"` remains supported as an optional vote; `rating` is no longer required when an event is supplied.
  - For a graded unit, a single-ref `knowledge_explain` returns `kind: "graded_unit"` with `ref`, `unit_ref`, `feedback_ref` (equal to `ref`), `id`, `revision`, `frontmatter`, `content`, and `inherits_from_closure`. It does **not** return legacy `first_block_ref` / `previous_block_ref` / `next_block_ref` navigation (which applies only to legacy task/block references). Always record `id` (`unit_id`) and the integer `revision` when citing a rule; those two fields are the whole revision identity.
- **Three-Valued `conditions` Evaluation (`matched` | `mismatched` | `condition_unknown`)**:
  - Units separate functional `tier` (`L1` axioms & probes, `L2` SOPs, `L3` convergence workflows, `L4` exploration mutators) from `evidence_strength` (`hardware_spec` | `reproduced_empirical` | `single_observation` | `hypothesis`).
  - Query evaluates the exact condition keys declared in each unit's `conditions` mapping (such as `soc`, `cann`, `driver`, `framework`, `repository`, `revision`, `workload_scope`, `dtype`, `input_shape`, or `workload_case_sha256`; never assume a hardcoded legacy condition-key list). Inherited `_common/` rules evaluate their own declared `conditions` independently without widening scope.
  - **`condition_unknown` != Match**: `condition_unknown` occurs when either a declared `required` premise on the unit or the caller's `observed` fact is `"unknown"`, missing/not supplied, or has an incomparable format, and `unknown == unknown` never matches (an absent requirement or `"any"` is unconstrained `matched`, and historical `required: "unknown"` is never backfilled by later machine versions). Verify whichever fact is missing or unknown (e.g., source `repository`/`revision` for an `L2` source SOP, or runtime environment for an NPU rule)—**never** treat `condition_unknown` as an automatic match.
- **Explicit Selected-Evidence Distillation (`knowledge_distill`) & Multi-Domain Authorization Boundary**:
  - `knowledge_distill(inputs, task_state, request_nonce, domain=..., related_refs=[...], proposal=...)` distills caller-selected, already-authorized evidence (`inputs` items with `kind` in `experiment_ledger | run_manifest | authorized_transcript | ecosystem_repo | hardware_spec | ablation_receipt`, `outcome` in `observed | verified | compile_failed | infra_failed | measurement_invalid | in_flight`, `source_locator`, `content`, `evidence_refs`, optional `repetitions >= 1`) under the active `/mindie-agent` capture lease (`SummaryLedger`) for the default or explicitly activated target `domain`. Optional `related_refs` names existing stable unit IDs or graded references for same-topic delta comparison before distillation, so the result revises or merges an existing unit instead of duplicating it. Optional `proposal` submits a `mindie-distill-decision/1` foreground decision for deterministic validation and local application with `model_calls=0`; it is not a substitute for the selected evidence or for local authorization. Writing/distilling to a registered non-default `domain` requires that target domain's own existing `consent` and `project_root` scope plus `mindie_entry(op="init", domain="<domain>", request_nonce=...)`; ordinary reads never widen authorization.
  - Use `task_state: 'verified_milestone' | 'completed'` (the runtime wire token for the verified milestone is `"verified_milestone"`): `observed` as well as fault/environment/build evidence (`compile_failed`, `infra_failed`, `measurement_invalid`) can be distilled into `single_observation` or `hypothesis` (preserving its true `evidence_strength` without elevating unverified fault/build evidence to `hardware_spec` or `reproduced_empirical`; `hardware_spec` specifically requires a `hardware_spec` source, `reproduced_empirical` specifically requires `outcome == "verified"` with `repetitions >= 2`, and `L4` specifically requires a verified `mindie-bench-ablation/1` receipt). Only `task_state="in_flight"` (or all-`in_flight` / empty inputs) is a deterministic zero-call `noop`, and an ordinary host `Stop` event is **not** task completion. Local receipt/application failures preserve a completed native model result (`operation_status="local_receipt_failed"` or `"local_application_failed"`, `local_error`) without replaying the paid call.
  - **Release Boundary**: `knowledge_distill`, multi-domain routing, and graded `knowledge_query` options (`domain_path`, `token_budget`, `include_unknown`, `include_archived`) depend on the paired `mindie-knowledge 0.13.0` runtime. It supports graded Git publication (`mindie-publication-contract/2`), independent Feed sync, and revision-bound unit feedback (`feedback_ref` / `/units/<id>@<revision>`). The selected feed revision and installed runtime identity are separate facts; use their own receipts to verify them.

## Diagnosis and exploration

Knowledge tiers describe use, not a mandatory execution order. Apply complete,
condition-matched prerequisites; select L3 branches from observations. Hermes
can revise any tier, and an exploration finding may be L1, L2, L3 or L4.

Read [Diagnostic Reasoning](diagnostic-reasoning.md) when the routine path no
longer explains the evidence, accuracy depends on state/observation, or a
milestone challenges existing knowledge. It covers discriminating experiments,
first divergence, observer controls, sequence reproducers, independent oracles,
and preserving corrections. Keep evidence validity, goal attainment and
reusable information distinct. Repeated no-information attempts prompt review;
new facts are progress even without a performance improvement.

Use `task_state="verified_milestone"` for a finished sub-result in a continuing
task. `in_flight` and all-pending inputs remain no-op; Stop is not completion.
Keep supported/refuted/inconclusive judgments with their scope and source.
Only L4 transformation admission requires the verified final-combination
ablation receipt; diagnostic findings need the evidence appropriate to their claim.

## Long-Horizon Fact References & NPU Timing / Profiler Discipline

- **Launch-Time `in_flight_runs` Registration & Recovery-First-Query (`PROGRESS.md` + `experiment-ledger.jsonl`, No Second State Machine)**:
  - `coordinator` (`Run Manifest` / `run_id`, where `run_id == execution_id` at `client.run` submit and is never replaced) and `remote-dev` (`job_id`) are the sole source of truth for execution state.
  - **At Launch**: Immediately upon starting a run or job (before waiting or ending the turn), atomically update `PROGRESS.md` (`os.replace`) to record `{run_id, job_id, slot_id, host_endpoint, manifest_path, started_at}` under `in_flight_runs`, together with the task goal, current workspace `git_commit`/`diff_digest`, verified baseline `run_id`, best verified candidate `run_id`, key historical `conditional_avoid` refs, and next minimal experiment.
  - **On Recovery / Compaction**: Read `PROGRESS.md` `in_flight_runs` first and query the original `run_id` / `job_id` (`TaskClient.observe(run_id=...)` / `remote_job_status`) before taking any action—**never** resubmit a command while its `run_id` is in flight or uncertain.
  - **Single-Writer `experiment-ledger.jsonl` & Sequential Pruning Consumer Rule**: Append one JSON record per experiment linking `task_id`, `exp_id`, `run_ids`, `hypothesis`, `factors`, `factor_roles` (`performance` | `correctness_required` | `dependency` | `inseparable_group`), `unit_refs` (`unit_id` + integer `revision`), `receipt_refs`, `run_status`, `judgment` (`supported` | `refuted` | `inconclusive`), `scope_conditions`, and optional `conditional_avoid` / `supersedes_exp_id`. Local receipt/ledger errors never overwrite a succeeded remote result. In Contract C4 (`AblationReceipt`), LOO `delta <= tolerance` only sets `disposition: "candidate_for_sequential_pruning"`; consumers **must** treat `disposition == "candidate_for_sequential_pruning"` with `pruned_combination_verified == false` as **RETAIN**.
- **Pre-Compile Parallelism, Physical NPU Timing Mutual Exclusion & Profiler Discipline**:
  - Confirmed device-free compilation and log inspection may run concurrently using isolated `MINDIE_SLOT_ID` caches. Compiler names do not prove device independence; device JIT, probing and warmup need the existing lease and actual allocation.
  - Any benchmark or profiling run that claims latency, TPOT, TTFT, MFU, or bandwidth numbers **must** acquire an exclusive `coordinator` lease on the target physical NPU cards (including dual-Die `Phy-ID` sibling isolation on Ascend A3 910C) and pass pre/post `environment_fingerprint` checks.
  - **Explicit Unlabeled or Labeled Windows (`segment.py`), Scene/Clock Annotations & Unverified `msmodeling` Provider**: `python -m mindie_profiler` supports **explicit unlabeled time windows** (`--time-window START:END` / `--window START:END`), **explicit labeled step windows** (`--step-window STEP=START:END` / `--step STEP=START:END` / `--steps-file`), and explicit `--full-range` (in `--unit us|ns|ms`). Not every analysis requires step labels, and `segment.py` **never** infers real step identity from kernel rows, timestamps, or CSV headers. Scene metadata (`--mode`, `--framework`, `--phase`, `--tp`, `--dp`, `--graph-mode`, `--clock-domain`, `--input-signature`) uses explicit caller annotations and reports `uncertain` otherwise (`scene_detector.py`). Missing `--clock-domain` on multi-rank DBs emits `clock_domain_unknown`, and `compare.py` refuses cross-run timing comparison unless `clock_domain` matches. `theoretical_model.py` separates `ideal_hardware_lower_bound_ms` (local `roofline-max-v1` single-kernel bound, not a whole-network bound), `model_predicted_ms` (only from an injected validated external provider with real version, matching protocol, matching `input_signature`, and non-empty evidence; otherwise `None` with `unmodeled_reason`), and `measured_device_ms`; `probe_msmodeling_adapter` reports install state only and never imports/executes `msmodeling` (`verified=False`). Never infer thermal throttling from a static `85°C` threshold (`used_as_throttling_proof=False`); when explicit throttle signal bits are unavailable, report throttling status as `unknown` / `measurement_limitations`.
